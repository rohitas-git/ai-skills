# Generate and maintain a real verification recipe

## Generation

Inspect the selected repository surface, native launch/drive commands, fixtures/auth, readiness,
observable effects and instance isolation. Reuse an existing harness before inventing one. Missing
build, seed or access prerequisites are blockers; repairing the product, adding dependencies or
applying migrations does not follow merely from a documentation request.

Let `/1-runtime-feature-map` author the selected user paths, alternate entries, actual selectors/
commands, preconditions, expected result and gotchas. Let `/0-skill-creator` author a requested
project-local verification skill. Its launch, doctor, drive, evidence and cleanup sections must use
real project commands, with helpers executable and their invocations documented. Write for the next
agent reading cold. A generated recipe remains a draft until an authorized execution proves it.

Within execution scope, run launch→identity/doctor→one selected real feature→action/result evidence→
owned cleanup, then read the evidence after teardown. Empty-data startup includes actual required
seed/readiness, not just an answering port. A stand-in environment leaves target-only setup steps
explicitly unverified. A successful convenient entry point does not cover all mapped entry points.
Select a smoke path that crosses the newly documented control or setup boundary, and identify the
target instance in the evidence so the next reader can match it to the recipe.

## Maintenance

Pin the existing map and requested coverage. Compare its index with actual feature files and scoped
source churn. Reconcile missing, duplicate, extra and renamed entries using real source evidence.
Source readers return a feature summary, entry points, likely drift and one runnable recipe; serial
review is valid, and delegation requires explicit authority and independent outputs.

Group recipes into the fewest safe app states. One coordinator drives a shared instance serially;
short-lived CLI journeys may use separate isolated sessions. Doctor before first use, after surprising
behavior or failed drives, and for fresh sessions. A healthy process can still have a wedged UI, so
restore a known state instead of assuming health proves usability. Keep evidence through every cleanup.

Separate map drift, harness gaps, product regressions and unreachable prerequisites. A selected path
with failed auth/seed data is BLOCKED, not verified-unreachable success. Record the attempted route
and missing prerequisite. Fix only the authorized documentation/harness scope; re-drive a changed
harness before calling it proven. Product repair returns as a separate accepted slice.
Repeat setup from a clean owned session when the launch, seed or doctor contract changed. When
updating a shared selector or fixture, re-drive the affected mapped entries in scope before calling
their evidence current.

Return clean only when the promised source and live coverage actually completed. Otherwise give
changed/partial/blocked outcomes per entry, remaining gaps and owned teardown. No automatic PR,
schedule, migration, install or publication follows from maintaining a recipe.
