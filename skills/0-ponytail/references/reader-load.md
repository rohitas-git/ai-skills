# Reader load and justified subtraction

Two costs matter: layers a reader traces and state a reader must hold in mind. Ask where a value
comes from and what can change it. Collapse a pass-through layer only when it hides no required
policy, compatibility, ownership or test seam. A single caller or implementation is evidence to inspect,
not a deletion rule. Prefer locals and returned values to broader mutable state when behavior permits.

Concentrate a repeated decision in one authoritative place. Derive synchronized values when possible.
Before adding a new branch or abstraction, inspect dead code, stale references and duplicated policy
inside the authorized change. Remove only what is proven unnecessary and owned by this task.

Sequence useful subtraction before the reshape when each step stays reviewable and verifiable.
Do not remove a trust-boundary validator, error path, accessibility behavior or contract merely because
the successful path can run without it. Do not delete unrelated files or a meaningful reference as
cleanup. A larger direct expression can be simpler than a terse abstraction with hidden ordering.
