# Pstack video notes for the skill framework

The strongest next improvement is to test a full Butler handoff through to user-visible evidence in a small app. The catalog already has playbook composition, project checkpoints and verification recipes. The walkthrough shows why those pieces matter together. It also suggests two practical additions: a ready-to-send prompt from Butler and a way to tell whether a selected workflow step ran, was skipped, or was blocked.

## Directory and ownership decisions

Pstack's installation manifest points at `skills/` and `agents/`. `poteto-mode` owns its playbook references, and host features supply some execution mechanics. The guide gives people realistic examples and common pitfalls. That separation is useful for a catalog targeting more than one host. [pstack manifest](https://raw.githubusercontent.com/cursor/plugins/main/pstack/.cursor-plugin/plugin.json) · [Official guide](https://github.com/cursor/plugins/tree/main/pstack/docs/guide)

| Concern | Existing home | Suggested direction |
|---|---|---|
| Find a route or prompt | `skills/0-butler/` | Keep the single Butler and its menu. Include recipe, owner, first action and a ready-to-send prompt when it saves a second round of translation. |
| Compose a workflow | `skills/0-butler/references/playbooks/` | Keep workflow ordering and completion evidence here. Link operational instructions to their canonical owner. |
| Execute one job or apply a principle | `skills/<name>/SKILL.md` and `references/` | Keep the thin skill body and conditional detail. Link a principle where it influences a step. The existing depth prefix identifies ownership and does not need another directory hierarchy. |
| Run a custom helper | The owning skill's `scripts/` or shared catalog `scripts/` | Keep supported invocation and required inputs near the caller. A helper returns an observation or file. The caller interprets that output before advancing the workflow. |
| Capture project evidence | The consuming repository's app harness, feature map and task record | Keep project commands, fixtures and evidence paths with the app. Keep the generic procedure in the catalog. Link from the existing task checkpoint instead of copying the evidence. |
| Distribute and document | `hubs/`, `guidelines/`, `wikis/`, host sync tooling | If a distributable plugin is needed, pilot one host and package one usable workflow with its reference dependencies. Verify in a clean target and check missing-connector behavior. Keep archived vendor material out of active discovery. |

These homes follow the existing [catalog layout](../layout.md), [Butler handoff](../../skills/0-butler/references/playbooks.md), [tool ownership](./pstack-tooling.md) and [project continuity](../../skills/0-implement/references/project-continuity.md).

## Suggested sequence for improving the catalog

1. **Prove one real workflow.** Use a disposable app fixture with a concrete CSV or similar export bug. Check that the actual entry point reproduces the bug, that the regression check fails for the expected reason, and that the fixed run produces the expected output. Save the receipt and a checkpoint, then test pickup from a fresh session. This exercises connections whose current review is structural. [Runtime verification workflow](../../skills/0-implement/references/verification-workflows.md) · [Current Butler eval limits](./butler-routing-2026-11-18.md) · [Continuity evidence](./project-continuity-2026-11-18.md)
2. **Improve the handoff using the trial.** Try an optional runnable prompt with goal, target, known facts, constraints, done check and expected evidence. Ask the execution owner to record only decision-changing steps and why any required evidence was unavailable. Keep this in the existing plan or checkpoint. [Butler query workflow](../../skills/0-butler/references/query-workflow.md)
3. **Make one failure preventable.** If a resumed run trusts an invalidated receipt or claims success from a build alone, add a representative case and strengthen the responsible check or instruction. Review a matched before/after run against the same rubric and retain failed attempts. Expand after the pilot shows what helps. [Skill evaluation](../../skills/0-skill-creator/references/pstack-authoring-and-evaluation.md) · [Recurring corrections](../../skills/1-agent-workflow-observer/references/recurring-corrections.md)
4. **Package a narrow workflow if distribution is needed.** Choose one host and verify Butler or the receiving owner can load its recipe, resolve specialists and references, find the permitted tools, and report a blocked check when those tools are missing. Prefer a small reproducible install test before adding host-specific orchestration. [Catalog sync tooling](../../scripts/README.md)

An original pilot prompt for this framework:

> In the disposable orders app, the CSV export duplicates some orders after a retry. Reproduce it through the export entry point before editing. Keep filters and sort behavior intact. Done means the retry fixture yields exactly the expected ordered IDs with zero duplicate IDs. Capture the failing and passing commands, row counts and output artifact. Stop after local verification and save the next step in the existing checkpoint.

These are research notes. The proposed pilot, live plugin installation, model trials and app verification remain unrun.
